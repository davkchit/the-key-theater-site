# Театр Ключ — контекст проекта

Этот файл — для того, чтобы кто угодно (человек или другая нейросеть/другой аккаунт Claude),
открыв этот репозиторий без какой-либо истории переписки, за одно чтение понял: что это за
проект, что уже сделано, что нет, что заблокировано и почему всё устроено именно так, а не
иначе. Технический README.md (стек, команды, структура папок) не дублируется здесь — см. его
отдельно. Здесь — контекст и решения, которых в самом коде не видно.

## Что это за проект

Сайт молодёжного театра «Ключ» (Набережные Челны, Татарстан). Некоммерческая организация,
небольшой бюджет. Разработчик — один человек, делает сайт **разово**: после сдачи проект
"уходит в свободное плавание", дальнейшей платной поддержки не предполагается. **Это ключевое
ограничение, которое определило почти все архитектурные решения ниже** — везде, где был выбор
между "проще прямо сейчас" и "не потребует присмотра через год", выбиралось второе.

## Технически это две независимые системы

Самое важное для понимания архитектуры: на сайте по факту работают **две никак не связанные
друг с другом трубы данных**. Единственное, что их объединяет — это сам посетитель сайта,
который одной рукой смотрит контент, а другой заполняет форму.

### Труба 1 — как контент попадает на сайт

```
Сотрудник театра ──(форма в /admin)──┐
                                       ├──> GitHub (репозиторий) ──> GitHub Actions (сборка)
Разработчик ──(git push)─────────────┘                                      │
                                                                              ▼
                                                              хостинг (сейчас GitHub Pages,
                                                              план — Beget) ──> зритель
```

- Контент (репертуар, афиша, курсы, команда, галерея, награды, настройки) хранится не в коде,
  а в JSON-файлах: `src/content/*.json`. Старые файлы `src/data/*.ts` теперь просто читают эти
  JSON и отдают наружу под тем же именем/типом — ни один компонент переписывать не пришлось.
- Редактирование этого контента — через **Decap CMS**, страница `/admin` на самом сайте
  (`public/admin/index.html` + `public/admin/config.yml`). Сотрудник заходит, видит формы под
  каждый раздел (Репертуар/Афиша/Курсы/Группы курсов/Команда/Галерея/Награды/Настройки),
  правит, жмёт "Сохранить" — и это на самом деле коммитит изменения прямо в GitHub-репозиторий.
- Почему Decap, а не Strapi/самописный бэкенд: тот вариант — это живой сервер + база данных,
  которые кто-то должен патчить и следить за ними годами. С разовой разработкой без поддержки
  это плохая идея (упадёт — некому будет поднимать). Decap ничего не хостит сам, только
  коммитит в git — обслуживать нечего.
- Почему не просто Google Sheets как источник контента: для простых списков (например,
  тумблер вкл/выкл) хватило бы, но для карточек с фото+текстом (состав команды, описания
  курсов) это неудобно и не даёт нормальной загрузки/обработки изображений.
- Картинки, которыми управляет CMS, лежат в `public/uploads/...` (обычные файлы, не
  Vite-импорты) — так Decap может писать туда новые загрузки напрямую. Иконки/декор, которые
  сотрудники не должны менять (например, иконки курсов), остались обычными
  Vite-импортами в `assets/`.

**Статус трубы 1:**
- ✅ Конфиг Decap CMS + перенос всего контента в JSON — готово.
- ✅ Локальное тестирование CMS работает (см. ниже "Как пощупать CMS").
- ⏳ **OAuth-прокси для GitHub-бэкенда Decap не настроен.** В `public/admin/config.yml` стоит
  заглушка `base_url: https://REPLACE-ME.netlify.app`. Без неё сотрудник не сможет реально
  залогиниться и сохранить изменения на настоящем сайте (сейчас CMS работает только в
  локальном режиме на компьютере разработчика). План: завести **отдельный бесплатный Netlify-
  сайт исключительно для этого хендшейка** (не хостить там сам сайт — см. ниже почему), включить
  там Identity + GitHub-провайдер, вписать адрес в конфиг.
- ⏳ **Публикация сайта на Beget не подключена.** Сайт физически всё ещё на GitHub Pages
  (`vite.config.ts` имеет `base: '/the-key-theater-site/'` — костыль именно под GitHub Pages).
  План: GitHub Actions при пуше собирает `dist/` и заливает на Beget по FTP/SFTP (или через
  нативный git-деплой Beget, если он у них есть — надо проверить в панели). Нужен доступ к
  Beget (данные хостинга) от клиента.
- ⏳ Когда переедем на Beget: сменить роутер с `createHashRouter` на `createBrowserRouter`
  (`src/router.tsx`, комментарий там же объясняет зачем) и убрать/поменять `base` в
  `vite.config.ts`, добавить `.htaccess` с rewrite на `index.html`.

**Почему не Netlify/Vercel/Cloudflare Pages как хостинг сайта** (важно, чтобы не предлагать
это снова): аудитория сайта — это зрители из Набережных Челнов, то есть 100% российская.
Хостить сам сайт на западном CDN — риск, что часть зрителей будет иметь нестабильный доступ
без VPN, а заставлять зрителей включать VPN ради афиши — плохо. Плюс оплата западных сервисов
российской картой не работает. Поэтому сайт целиком остаётся на российском хостинге (Beget,
уже куплен клиентом), а Netlify используется **только** как крошечный сервис авторизации для
редактора CMS — то есть его касается только сотрудник, который редактирует контент, а не
зрители.

**Риск блокировки GitHub в России** — обсуждался отдельно. Вывод: сборка (GitHub Actions)
не пострадает никогда, потому что она выполняется на серверах самого GitHub, а не через
российские сети. Уязвимо только само редактирование через `/admin` (браузер сотрудника должен
достучаться до github.com) — и даже это деградирует мягко (в крайнем случае — разовый VPN для
одного человека при сохранении правок), сайт для зрителей продолжит работать в любом случае.

### Труба 2 — как данные о зрителях попадают в таблицу

```
Зритель → форма на сайте (или клик по коту-помощнику)
        → fetch() напрямую в Google Apps Script Web App
        → дописывает строку в Google-таблицу театра
```

Это работает независимо от GitHub/Beget/Decap — отдельный, уже давно работающий механизм.
Код — `src/data/sheetsForms.ts`. Отправка идёт `mode: 'no-cors'` + `Content-Type: text/plain`
(иначе Apps Script не отвечает на CORS preflight) — из-за этого ответ сервера непрозрачен,
успех предполагается оптимистично сразу после отправки запроса.

**Типы форм (`SheetFormType`):**
- `courses` — запись на курс (`SignupForm.tsx`)
- `festival` — заявка на фестиваль «Действующие лица» (`FestivalSignupForm.tsx`)
- `audience` — подписка "держите в курсе" на странице контактов (`AudienceSignupForm.tsx`)
- `mascot` — клики по вопросам в коте-помощнике и свободные вопросы (см. ниже). **Новый тип,
  добавлен в этом проекте, но на стороне Apps Script (он вне этого репозитория, на
  script.google.com) для него ещё нет листа/колонок.** События сейчас улетают в никуда молча
  (no-cors скрывает и успех, и ошибку). Нужно либо получить доступ к скрипту и доделать самому,
  либо чтобы клиент добавил лист под `mascot` по аналогии с остальными.

## Кот-помощник (Mascot.tsx)

Виджет внизу справа на каждой странице. Изначально был просто деревом меню (категория → список
вопросов). Сейчас — **поиск с автодополнением**: поле ввода, под ним до 5 подходящих вопросов
(простое совпадение подстроки по `label`, без ИИ — осознанное решение, см. ниже).

- Данные вопросов-ответов — `src/data/mascotMenu.ts`. Часть ответов статичные, часть
  вычисляются на лету из данных сайта (например, "что идёт сейчас" читает текущую афишу) —
  поэтому не протухают сами по себе.
- Если по запросу 0 совпадений — показывается поле "напишите свой вопрос", тоже уходит в Sheets
  (тип `mascot`, см. трубу 2 выше).
- Каждый клик по найденному вопросу тоже трекается в Sheets — так можно будет со временем
  увидеть, что реально спрашивают чаще всего, и добавить это в базу вопросов.
- **Почему не настоящий ИИ-чат:** обсуждалось отдельно и осознанно отклонено. Причины: для
  проекта без поддержки после сдачи — постоянные расходы на API, риск что бот наврёт что-то
  про театр, некому будет присматривать/поправлять. Поиск по ключевым словам справляется с
  задачей клиента ("узнать частые вопросы и закрыть их") без этих рисков.
- **Сама картинка кота (`assets/mascot.png`) — временная заглушка.** Сейчас это статичное
  изображение, покачивается только через CSS (`animate-kl-float`). Клиент должен прислать
  реальные кадры/спрайты анимации ходьбы — после этого нужно завести настоящую sprite-анимацию
  (или CSS keyframes по кадрам) в `Mascot.tsx` вместо простого `<img>`.
- Визуал: рамка "от руки" — `src/components/ui/SketchyFrame.tsx`. **Важный технический урок**:
  первая версия рисовала рамку одним SVG-путём, растянутым по обеим осям
  (`preserveAspectRatio="none"` на непрямоугольном контейнере) — это ломает геометрию обводки в
  Chromium (линия расползается по диагонали). Исправлено на 4 независимые полоски (по одной на
  каждую сторону), каждая растягивается только вдоль своей оси — тот же приём, что уже
  использовался в `WavyUnderline.tsx`. Если будешь трогать декоративные SVG на сайте — не
  растягивай обводку (stroke) сразу по двум осям, только заливку (fill) можно.

## Оплата билетов / касса — на паузе

Изначальный план был просто встроить виджет Билетона. Клиент выяснил, что через Билетон
театр теряет возможность собрать свою базу зрителей (их условия обработки ПД не позволяют
передавать контакты третьим лицам полноценно — максимум имя+почта без телефона, с
ограничением на количество писем). Разбирали варианты (спросить у Билетона напрямую про
доступ к данным / форма-шлюз перед оплатой / полная своя касса с фискализацией по 54-ФЗ) —
решили **пока ничего не делать по оплатам**, ждём решения от человека по имени **Ваня**
(изучал онлайн-кассы) и бухгалтера клиента. **Не начинать интеграцию оплат, пока явно не
попросят** — это было прямое указание клиента, чтобы не делать работу впустую.

Если/когда до этого дойдёт — клиент попросил фиксировать по каждой покупке: дата посещения,
спектакль, имя клиента, телефон, почта, количество билетов.

## Как пощупать CMS локально (без реального хостинга/OAuth)

Decap поддерживает `local_backend: true` (уже включено в `config.yml`) — вместо GitHub CMS
просто пишет файлы на диск через маленький локальный прокси.

```bash
npm run cms:server   # в одном терминале — локальный прокси Decap (порт 8081)
npm run dev           # в другом терминале — сам сайт
```

Открыть `http://localhost:5173/admin/` (без `/the-key-theater-site/` в пути — под `/admin/`
эта часть Vite-конфига не действует). Логина спрашивать не будет. Сохранение реально пишет в
`src/content/*.json` и `public/uploads/`.

⚠️ Если запускать `npm run dev -- --host` — это открывает dev-сервер всей локальной сети, а
у `/admin` в локальном режиме вообще нет пароля. Не делать это на публичном/чужом wifi.

## Прочие реализованные детали

- **Тумблер фестиваля** — `src/content/settings.json` → `festivalApplicationsOpen`, читается в
  `src/pages/AboutPage.tsx`. Когда `false`, кнопка "Стать участником" превращается в заглушку
  "Приём заявок закрыт".
- **Шрифты** — Oswald и Manrope уже самохостятся через `@fontsource/*` с поддержкой кириллицы
  (`src/styles/index.css`), менять не нужно, даже если кто-то пришлёт файлы шрифтов "на
  замену" — это те же самые шрифты.
- **Логотип-бейдж** (`assets/logo-badge.svg`) — круглая эмблема "КЛЮЧ" в шапке сайта. Заменена
  с растрового PNG на SVG (обрезан от исходного A4-экспорта из CorelDRAW, где сам значок занимал
  маленький кусок листа). Важный нюанс: буквы/спираль в оригинале — не белая заливка, а
  прозрачные "дыры" в чёрной фигуре (fill-rule: evenodd) — на белой печатной странице это
  смотрелось нормально, но на тёмной шапке сайта дыры показывали тёмный фон вместо белого.
  Починено: добавлен белый круг под чёрной фигурой в самом SVG — теперь дыры показывают белый
  цвет независимо от фона позади. Есть ещё два логотипа в проекте (текстовый wordmark в
  подвале/моб. меню, отдельный keymark на странице курсов) — они пока остаются старыми PNG,
  SVG-версий для них не присылали.

## Известные технические долги / что можно улучшить, но не срочно

- Бандл JS ~620kB — Vite ругается на размер чанка. Не критично для маленького сайта, но можно
  когда-нибудь разбить через `dynamic import()`.
- `assets/logo-wordmark.png` и `assets/logo-keymark.png` всё ещё растровые.
- Поиск в коте-помощнике — простое совпадение подстроки, не понимает синонимы/опечатки. Если
  вопросов станет много (обсуждали 300-500), стоит добавить ключевые слова-синонимы на каждый
  пункт для лучшего совпадения — но это уже contentная работа (наполнение), не архитектурная.

## Инструменты, которые пригодятся при доработке

В этой сессии выяснилось, что для визуальной проверки вёрстки/SVG стоит не полагаться на
рассуждения "по логике должно сработать", а реально рендерить. Работающий способ в этом
окружении: `sharp` (рендер SVG в PNG) и `playwright` + Chromium (скриншот реальной вёрстки
через `file://`, работает даже когда обычный сетевой доступ к localhost из инструментов
недоступен). Оба ставятся через `npm install` в любую временную папку, в зависимости самого
проекта добавлять не нужно.
