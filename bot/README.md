# Telegram-бот театра «Ключ»

Отвечает на вопросы по данным сайта, записывает на курсы и присылает заявки
администратору в Telegram-группу с кнопками статуса. Работает на n8n,
модель — YandexGPT.

Главный принцип: **модель разговаривает, код записывает.** Нейросеть только
отвечает на вопросы и ставит метку («хочет записаться», «позовите человека»,
«не нашёл ответа»). Имена, телефоны, статусы и шаги записи ведёт обычный код,
поэтому странные вопросы в худшем случае дают ответ «уточнит администратор»,
а не мусор в заявках.

## Что где лежит

| Путь | Что это |
|---|---|
| `core/lib.js` | Вся логика: кнопки, сценарий записи, лимиты, промпт, разбор ответа модели |
| `core/faq.md` | Справка, которой нет на сайте (история, контакты, ЛСД, лагерь) и список того, на что бот не отвечает сам |
| `core/knowledge.mjs` | Собирает данные для бота из `src/content/*.json` — афиша, спектакли и курсы берутся с сайта, не дублируются |
| `scripts/publish-knowledge.mjs` | Кладёт `public/knowledge.json` рядом с сайтом — запускается из `npm run build` |
| `scripts/build-workflow.mjs` | Генерирует workflow n8n: вшивает `lib.js` и данные в узлы |
| `workflows/*.json` | Готовые workflow для импорта в n8n (генерируются, руками не править) |
| `scripts/simulate.mjs` | Прогон диалога через логику и настоящий YandexGPT, без n8n |
| `eval/cases.json` | Набор вопросов, на котором проверяется бот перед каждым выкатом |
| `scripts/eval.mjs` | Прогоняет набор через живую модель, считает пройденное и сравнивает с прошлым прогоном |
| `eval/intents.json` | Размеченный набор фраз для парсера намерений |
| `scripts/parse.mjs` | Разбор намерений: потыкать фразами или прогнать весь набор со счётом |
| `scripts/test-flows.mjs` | Детерминированные проверки сценариев, без модели и без сети |
| `scripts/e2e-local.mjs` | Сквозной тест настоящего n8n с поддельным Telegram |
| `scripts/n8n-local.mjs` | Запуск n8n с ключами из `.env.bot` |
| `scripts/poll-telegram.mjs` | Мост для теста с телефона без публичного сервера |

## Какая модель отвечает

Провайдер — это три настройки, а не три куска кода (`bot/core/llm.mjs`).
Yandex, Groq и почти все остальные говорят на одном OpenAI-совместимом формате.

**Groq** — бесплатный тариф, быстрый, по-русски пишет живее:
```
LLM_BASE=https://api.groq.com/openai/v1
LLM_AUTH=Bearer
LLM_KEY=<ключ Groq>
LLM_MODEL=llama-3.3-70b-versatile
LLM_PARSER_MODEL=llama-3.1-8b-instant
```

**Яндекс** — в России, платный:
```
LLM_BASE=https://llm.api.cloud.yandex.net/v1
LLM_AUTH=Api-Key
LLM_KEY=<ключ Яндекса>
LLM_MODEL=gpt://<folder>/yandexgpt/latest
LLM_PARSER_MODEL=gpt://<folder>/yandexgpt/latest
```

Разные модели на ответ и на разбор — намеренно: у парсера крошечный промт и
простая задача, ему хватает младшей модели, а отвечать должна старшая.

Лимиты бесплатного Groq (сентябрь 2026): у `llama-3.3-70b` — 100 тыс. токенов в
сутки, это примерно **37 ответов в день**; у `llama-3.1-8b` — 500 тыс., на разбор
хватает с запасом.

Ключи — в `.env.bot` в корне репозитория (в git и Docker-образ не попадает):
`TELEGRAM_BOT_TOKEN`, `YANDEX_API_KEY`, `YANDEX_FOLDER_ID`,
`TELEGRAM_WEBHOOK_SECRET`, `ADMIN_CHAT_ID`, необязательно `YANDEX_MODEL`
(`yandexgpt` или `yandexgpt-lite`).

## Откуда бот берёт знание

```
админ правит афишу в CMS сайта
        ↓  коммит в git
npm run build → public/knowledge.json  (той же сборкой, что и страницы)
        ↓  раз в 10 минут
воркфлоу «Ключ · знание с сайта» → таблица kluch_knowledge
        ↓  на каждом сообщении
бот
```

Смысл в том, что **бот не может знать ничего, чего не показывает сайт** — файл
рождается той же сборкой, что и страницы.

Три свойства, ради которых это так устроено:

- **сбой загрузки ничего не ломает.** Скачалась ошибка вместо знания, файл
  обрезался, из справки пропал список запретов — прошлая копия остаётся
  нетронутой, бот продолжает отвечать по ней;
- **молчаливого протухания не бывает.** Если знание не обновляется, в чат
  администраторов приходит предупреждение (не чаще раза в 6 часов);
- **на чистой установке бот не нем.** В воркфлоу вшит снимок на момент
  сборки — он используется, пока не отработала первая синхронизация.

Адрес сайта задаётся переменной `SITE_URL` (по умолчанию `http://127.0.0.1:4173`).

Раньше знание было вшито в воркфлоу насовсем: театр добавлял спектакль,
сайт его показывал, а бот про него не знал, пока разработчик не пересоберёт
всё вручную. Ровно так бот и начинает врать.

### Запасной режим: документы театра вместо сайта

По умолчанию бот берёт знание **с сайта**. Если театр захочет присылать
афишу Word-файлом, включается запасной режим: афиша, расписание групп,
гастроли, фестиваль, лагерь, история и люди читаются из файлов

```
bot/docs/plan.docx     план сезона (таблица: дата | день недели | строки)
bot/docs/about.docx    «о нас»
bot/docs/people.docx   «о наших людях»
```

Запуск: `KNOWLEDGE_SOURCE=docs npm run knowledge`. Папка `bot/docs/` не
коммитится (репозиторий публичный, там имена людей). Новый план кладётся на
место старого с тем же именем; команда напишет, сколько показов нашла, и
перечислит строки, которые не смогла разобрать. Цены, описания спектаклей и
`faq.md` в этом режиме всё равно берутся с сайта. Код: `bot/core/docs.mjs`.

## Проверить, не стало ли хуже

Перед любым изменением промта, справки или логики:

```
node bot/scripts/test-flows.mjs                        # логика, бесплатно, секунда
node bot/scripts/eval.mjs --dry                        # то же плюс проверки ответов, без модели
node bot/scripts/eval.mjs --save=before                # замер «до» (~75 ₽, живая модель)
# ... правки ...
node bot/scripts/eval.mjs --diff=before --save=after   # что починилось, что сломалось
```

`--diff` разделяет три исхода: **починилось**, **СЛОМАЛОСЬ** и «формулировка
изменилась, проверки те же». Третье — норма, модель не обязана отвечать
дословно одинаково.

Прогоны лежат в `eval/runs/`. Выборочно: `--only=refusal,age`.
Дешевле для итераций: `--lite` (но сравнивать надо на одной модели).

Новый кейс добавляется в `eval/cases.json`. **Каждый пойманный баг должен
стать кейсом** — иначе он вернётся.

## Парсер намерений

Читает сообщение и возвращает структуру — намерение, нужные темы справочника,
возраст, название спектакля, — вместо того чтобы угадывать это регулярками.
**В боевом боте пока не включён**, живёт отдельно и проверяется руками:

```
node bot/scripts/parse.mjs "хочу записать дочку 7 лет" "а что в субботу?"
node bot/scripts/parse.mjs --lead "запишите ещё сына"   # как будто заявка уже есть
node bot/scripts/parse.mjs --set                        # весь набор со счётом
node bot/scripts/parse.mjs --set --lite                 # то же на дешёвой модели
```

Счёт на 53 фразах (17.09.2026):

| | намерение | возраст | тема | цена за разбор |
|---|---|---|---|---|
| YandexGPT Pro | 100% | 100% | 100% | ≈0,69 ₽ |
| YandexGPT Lite | 92% | 100% | 91% | ≈0,11 ₽ |

Две вещи, без которых это не работает:
- **`maxItems` у массива тем.** Без него младшая модель зацикливается и
  повторяет темы, пока не кончатся токены.
- **Проверка возраста по исходному тексту.** Lite отвечал «1» на «привет»;
  теперь возраст принимается, только если это число есть в самом сообщении.

Поля `answerable` в схеме намеренно нет: спрашивать модель, знает ли она ответ,
не показав ей справочник, — это просить её угадать. Решает код и отвечающий
вызов, у которого факты перед глазами.

**Каждое расхождение — повод либо поправить промт, либо поправить разметку.**
Половина первых ошибок оказалась моей неверной разметкой, а не ошибкой модели.

## Поменять ответы бота

1. Факты — в `core/faq.md`. Афиша, спектакли и курсы — в админке сайта.
2. `node bot/scripts/simulate.mjs` — посмотреть, как бот отвечает теперь.
3. `node bot/scripts/build-workflow.mjs` — пересобрать workflow.
4. Импортировать `workflows/kluch-bot.json` в n8n заново и опубликовать.

## Запуск на своём компьютере (для теста)

```
node bot/scripts/build-workflow.mjs
n8n import:workflow --input=bot/workflows/kluch-setup.json    # и kluch-errors.json, kluch-bot.json
n8n publish:workflow --id=kluchSetup000001                    # и kluchErrors00001, kluchBotMain0001
N8N_BIN=<путь к n8n/bin/n8n> N8N_HOME=<папка данных> node bot/scripts/n8n-local.mjs
curl -X POST http://127.0.0.1:5678/webhook/kluch-setup        # один раз: создать таблицы
node bot/scripts/poll-telegram.mjs                            # мост к Telegram
```

Администраторская группа: создать группу, добавить туда бота, написать `/id`,
вписать число в `ADMIN_CHAT_ID`, перезапустить n8n.

## Хранение

Встроенные таблицы n8n (Data tables): `kluch_chats` — состояние диалогов,
`kluch_leads` — заявки, `kluch_unanswered` — вопросы, на которые бот не
ответил (по ним раз в месяц дописывается `faq.md`). На боевом сервере в России
данные лежат в базе самого n8n.

## Защита

- Секретный заголовок от Telegram: чужие запросы на вебхук молча отбрасываются.
- Лимиты: 20 обращений к модели в день и 5 в минуту на чат, 150 в день на всех.
  При достижении общего лимита бот переходит на кнопки и шлёт тревогу в группу.
- Сообщения длиннее 500 символов обрезаются.
- Любое падение workflow — сообщение в группу администратора (workflow «Ключ · ошибки»).

## Известные ограничения прототипа

- Голосовые не распознаются (следующий шаг — Yandex SpeechKit).
- Токен Telegram передаётся через переменные окружения, а не через credentials
  n8n; для боевого сервера перевести на credentials.
- Стоимость курсов бот не называет — театр её не подтвердил.
